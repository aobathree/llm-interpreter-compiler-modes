# CLI版 vs REST API直接版 ベンチマーク

実施日: 2026-08-02 / 各条件 3 回計測（+ウォームアップ1回、実行間クールダウン8秒）
両実装とも同時fetch上限16。出力は1文字単位で同一。

| 銘柄数 | CLI版 中央値（最小〜最大） | 直接API版 中央値（最小〜最大） | 短縮 |
|---|---|---|---|
| 3 | 1.16s（1.09〜1.19） | 1.09s（1.08〜3.08） | 1.1x |
| 10 | 1.13s（1.13〜1.14） | 1.13s（1.09〜1.21） | 1.0x |
| 30 | 0.35s（0.35〜1.10） | 1.09s（0.27〜1.10） | 0.3x |
| 62 | 1.36s（1.17〜1.74） | **1.13s（1.10〜1.14）** | 1.2x |

## 考察

### 測定条件の注意：約1.1秒の「床」

この計測は午前中に大量のベンチマークを回した後に実施しており、単発リクエストの
レイテンシが通常0.1〜0.2秒のところ、**時折1〜7秒のスロットル・スパイク**が混ざる
状態だった（午前の初回計測時は単発0.09秒・3ペア0.11秒）。多くの実行が約1.1秒に
揃うのはこのため（1回の実行中に1個でも遅延リクエストがあると全体がそれに律速される）。
両実装とも同条件で計測しているので相対比較は有効だが、絶対値は保守的に読むこと。

### 結果の読み方

- **62銘柄では直接API版が安定して速い**（1.10〜1.14秒 vs CLI版 1.17〜1.74秒）。
  ばらつきの小ささが特に顕著で、リクエスト数削減（後述）と接続プーリングの効果とみられる。
- **小規模（3〜10銘柄）では差が出ない**。当初の仮説「プロセス生成＋TLS再ハンドシェイクが
  重い」は外れ——`bitbank` CLI 自体が Rust 製の薄いバイナリで、起動コストは
  ネットワーク待ちに埋もれる程度だった。**仮説は計測で潰す**。

### 実装過程で踏んだ2つの落とし穴（初版は CLI 版より遅かった）

1. **ureq の接続プール既定値**: ホストあたりのアイドル接続保持が既定1本しかなく、
   16並列の波ごとに15本がTLSハンドシェイクをやり直していた。
   `max_idle_connections_per_host` を並列数以上に設定して解消。
2. **リクエスト数の無駄**: 時足を3日分取得していたが、時足は「JST当日の出来高」
   計算にしか使われないため2日分（25時間以上カバー）で十分。
   1銘柄あたり 5リクエスト → 4リクエスト に削減（62銘柄で310→248）。

### 結論

REST API 直接版は、出力同一のまま 62銘柄で約1.2倍・分散大幅減。
ただし劇的な改善ではない——律速は依然ネットワーク（とレート制限）であり、
「呼び出し経路を1層削る」最適化の効果はその範囲に留まる。
コンパイルの深化は第2段（Rust化・並列化）で大半の果実を取り終えており、
第3段（直接API化）の限界効用は小さい、というのがこの実験の教訓。
