# CLI版 vs REST API直接版 ベンチマーク

実施日: 2026-08-04 / 各条件 3 回計測（+ウォームアップ1回、実行間クールダウン8秒）
両実装とも同時fetch上限16。出力は1文字単位で同一。

| 銘柄数 | CLI版 中央値（最小〜最大） | 直接API版 中央値（最小〜最大） | 短縮 |
|---|---|---|---|
| 3 | 1.13s（0.11〜1.22） | 1.14s（1.10〜1.16） | 1.0x |
| 10 | 1.19s（0.21〜1.31） | 1.11s（0.21〜1.14） | 1.1x |
| 30 | 1.13s（1.13〜1.18） | 1.13s（1.10〜1.18） | 1.0x |
| 44 | 1.13s（0.78〜1.14） | 1.14s（1.13〜1.22） | 1.0x |

> **注（2026-08-04 再計測）**: 対象を bitbank 公式取扱いの44銘柄（すべてJPY建て）に
> 訂正して再計測した。初出（2026-08-02）は tickers API が返す62ペア（旧ティッカー・
> BTC建てクロスペア含む）を対象としており、そのときは44→62のリクエスト増も相まって
> 62銘柄で直接API版が約1.2倍速かった。

## 考察

### 測定条件の注意：約1.1秒の「床」

この再計測も直前まで別のベンチマークを回した後に実施しており、単発リクエストの
レイテンシが通常0.1〜0.2秒のところ、時折スロットル・スパイクが混ざる状態だった。
多くの実行が約1.1秒に揃うのはこのため（1回の実行中に1個でも遅延リクエストがあると
全体がそれに律速される）。両実装とも同条件で計測しているので相対比較は有効だが、
絶対値は保守的に読むこと。

### 結果の読み方

- **44銘柄では壁時計時間はほぼ同等**（今回の条件では約1.0倍。同日のリソース計測では
  1.36秒 vs 1.12秒 = 1.2倍）。ばらつきは直接API版が一貫して小さく、
  リクエスト数削減（後述）と接続プーリングの効果とみられる。
- **小規模（3〜10銘柄）では差が出ない**。当初の仮説「プロセス生成＋TLS再ハンドシェイクが
  重い」は外れ——`bitbank` CLI 自体が Rust 製の薄いバイナリで、起動コストは
  ネットワーク待ちに埋もれる程度だった。**仮説は計測で潰す**。
- 壁時計時間の差が小さくても、**リソース消費は別物**（CPU時間34倍差。
  `results-resources.md` 参照）。

### 実装過程で踏んだ2つの落とし穴（初版は CLI 版より遅かった）

1. **ureq の接続プール既定値**: ホストあたりのアイドル接続保持が既定1本しかなく、
   16並列の波ごとに15本がTLSハンドシェイクをやり直していた。
   `max_idle_connections_per_host` を並列数以上に設定して解消。
2. **リクエスト数の無駄**: 時足を3日分取得していたが、時足は「JST当日の出来高」
   計算にしか使われないため2日分（25時間以上カバー）で十分。
   1銘柄あたり 5リクエスト → 4リクエスト に削減（44銘柄で220→176）。

### 結論

REST API 直接版は、出力同一のまま壁時計時間は同等〜約1.2倍・分散減。
劇的な改善ではない——律速は依然ネットワーク（とレート制限）であり、
「呼び出し経路を1層削る」最適化の効果はその範囲に留まる。
コンパイルの深化は第2段（Rust化・並列化）で大半の果実を取り終えており、
第3段（直接API化）の限界効用は小さい、というのがこの実験の教訓。
壁時計時間ではなくリソース消費の次元では大差がつく（`results-resources.md`）。
